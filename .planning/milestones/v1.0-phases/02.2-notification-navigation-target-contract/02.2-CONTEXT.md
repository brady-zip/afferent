## Phase Boundary

This phase does not build copied notification UI, change host delivery/outbox payloads, add router ownership, or reopen completed Phase 2 verification.

</domain>

<decisions>
## Implementation Decisions

### Closed Navigation Target
- **D-01:** Replace public `NotificationDto.entityId` with a required closed `target` union. A post target is `{ contractVersion: 1, kind: "post", postId, commentId?, label }`; a changelog target is `{ contractVersion: 1, kind: "changelog", slug, label }`.
- **D-02:** Status notifications target the post. Admin reply, comment reply, and mention notifications target the post with the source comment as an optional anchor. Changelog publication targets the public slug, never the component changelog ID.
- **D-03:** Every target has a server-authored human-readable accessible label. Post-only labels are `View feedback: {post title}`, anchored comment labels are `View comment on feedback: {post title}`, and changelog labels are `View changelog: {entry title}`.
- **D-04:** Bump `NotificationDto` from version 1 to 2 and `NotificationPageDto` from version 1 to 2 across public types, validators, generated references, fixtures, and tests. `DeliveryEventDto` remains version 1 with its host-consumable event identity; it is not a browser navigation contract.

### Server Resolution and Merge Normalization
- **D-05:** Resolve targets inside the component from the scoped `notificationEvents` source record and its post, comment, or changelog record. The browser and host wrapper do not resolve targets or issue per-row reads.
- **D-06:** Validate every resolved referent against the event scope and relationship. A missing or legacy-invalid optional comment anchor is omitted; a missing required post or changelog destination is an invariant failure rather than an ID leak or guessed URL.
- **D-07:** Preserve merge normalization by always moving `notificationEvents.postId` to the canonical post, rewriting polymorphic `entityId` only for `status_changed`, and retaining comment/changelog source IDs for their own target resolution. Legacy comment rows already clobbered by older merge behavior degrade to post-only targets.
- **D-08:** Both small and resumable merge cutovers must preserve this type-aware behavior. Notification pagination, unread counts, mark-read optimism, order, deduplication, and generation fencing otherwise remain unchanged.

### Headless and Navigation Boundary
- **D-09:** Headless hooks surface `NotificationDto.target` verbatim; they do not know routes, query component records directly, or reconstruct destination kind from event type/entity IDs.
- **D-10:** Phase 3 copied UI owns injected href construction from the closed target. Plan 03-03 must depend on this phase and may not use direct Convex reads or N+1 target lookups.
- **D-11:** Packed and registry fixtures consume the same exported target type so clean tarball installation proves the public contract.

### Security and Verification
- **D-12:** Start red with exact event-to-target matrices, cross-scope and mismatched-relation cases, version/validator checks, and small/resumable merge normalization.
- **D-13:** Add static guards rejecting `NotificationDto.entityId`, component-internal changelog IDs, browser target authority, UI/client target resolution, table scans, and per-notification direct reads.
- **D-14:** Run focused component, headless, merge-backend, packed-consumer, build/type/lint, and the complete Phase 2 regression. Preserve the unrelated dirty-worktree fingerprint exactly.

### the agent's Discretion
- Exact resolver/helper names and file decomposition are flexible when the target union, scope checks, version transitions, and one-read-path boundary remain exact.
- Test file placement may follow existing notification/merge suites or a focused new target-contract suite.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `notificationEvents` already stores `postId` plus the source `entityId`; all five event producers therefore contain enough server-side source identity to derive the closed destination.
- `toNotificationDto` is the single inbox projection point and already loads the event and initiator.
- Existing scope helpers, merge cutover machinery, public changelog slug/title records, notification pagination, and React generation fencing remain reusable.

### Established Patterns
- Stable DTOs are closed and explicitly versioned in both `src/client/contracts.ts` and `src/component/validators.ts`.
- Host-generated bindings accept resource intent plus local `sessionGeneration`; they never accept scope, identity, permission, or projection authority.
- Merge readers normalize source posts to canonical posts while preserving historical source records.

### Integration Points
- `src/component/notifications/inbox.ts` projects notification rows; all event producers under `src/component/notifications/**` establish the source relation.
- `src/component/model/merge.ts` currently rewrites `entityId` along with `postId` and must become event-type-aware.
- `src/react/hooks/notifications.ts`, bindings, generated references, packed fixtures, and exact static contracts must advance together.
- Phase 3 Plan `03-03` consumes the target to build injected post/comment/changelog hrefs without data fetching.

</code_context>
