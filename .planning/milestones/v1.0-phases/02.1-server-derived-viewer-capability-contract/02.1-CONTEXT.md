# Phase 02.1: Server-Derived Viewer Capability Contract - Context

**Gathered:** 2026-07-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Add the narrow trusted-host, component-read, versioned DTO, and headless React contract that lets Phase 3 copied UI render the current viewer's vote membership and author-only edit/withdraw availability truthfully. This phase does not build copied UI, add client authority inputs, reopen Phase 2 verification, or broaden administration policy.

</domain>

<decisions>
## Implementation Decisions

### Trusted Viewer Resolution
- Add an optional read-context resolver such as `resolveViewerActor(ctx)` to the scoped server client. It returns the same provider-neutral `VerifiedActor` shape as participation resolution, but is derived inside the trusted host query wrapper.
- The browser never supplies `actorId`, `userId`, `viewerActor`, capability booleans, or vote membership. Host-generated public function references remain authority-free.
- Component public reads accept the optional verified actor fact only from the host wrapper, locate an existing actor by the scoped `by_scope_external_key` index, and do not create or update actor records from a query.
- Existing `viewerAuthenticated` policy behavior remains compatible. Anonymous viewers and authenticated viewers without an existing Afferent actor receive all viewer capability fields as `false`.

### Viewer State Contract
- Add flat server-derived fields to post-bearing DTOs: `viewerHasVoted`, `viewerCanEdit`, and `viewerCanWithdraw`.
- `viewerHasVoted` comes from the same scoped `votes.by_scope_post_actor` membership truth used by the idempotent vote mutation.
- `viewerCanEdit` and `viewerCanWithdraw` are author capabilities computed server-side from actor ownership and the exact current post-state rules enforced by the participation mutations. The UI never compares `author.id` with a client-held identity.
- Apply the fields consistently to `PostDto` and `FeedbackPostDto` paths used by list/detail UI, including pages and post lookup results. Search/similar/roadmap/changelog projections remain minimal unless they expose these actions.

### Versioning and Headless Behavior
- Bump every affected DTO/container contract version explicitly; do not silently widen an existing versioned shape.
- Preserve provider neutrality and stable opaque string IDs. No provider record or component document crosses the contract.
- Vote optimism updates both `voteCount`/`totals.votes` and `viewerHasVoted` to the requested desired value across relevant feed/detail caches, with existing rollback/error behavior unchanged.
- Headless hooks surface the server fields verbatim. They do not invent a second membership or authorization state machine.

### Security and Verification
- Start red with actor/non-actor/anonymous and state-permission matrices for membership, edit, and withdraw; include an authenticated-but-not-yet-persisted viewer.
- Prove a client cannot spoof viewer identity or capabilities through browser arguments, bindings, validators, or session-generation fields.
- Prove vote toggle consistency, scoped indexed point lookups with no scan, exact DTO validators/version bumps, packed-consumer compatibility, and static guards against UI-local membership or `author.id === currentUser` authority reconstruction.
- Run the complete Phase 2 regression plus focused packed/headless gates. Treat this as a security-sensitive phase and require independent verification before Phase 3 resumes.

### the agent's Discretion
- Exact internal helper names and file decomposition are flexible when they preserve the locked trust boundary and observable contract.
- The planner may split contract, wrapper/headless, and adversarial verification work into multiple tasks, but the phase should remain one narrow executable plan if practical.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ClientResolvers.resolveActor` already establishes the provider-neutral trusted mutation resolver pattern; the new viewer resolver should mirror it for query contexts without reusing a mutation-only type.
- `actors.by_scope_external_key` and `votes.by_scope_post_actor` provide bounded indexed lookups for viewer resolution and membership.
- `toPostDto` and `toFeedbackPostDto` centralize post projection, while `applyVoteOptimism` centralizes feed vote optimism.

### Established Patterns
- Host wrappers derive scope, authentication, actor identity, and admin authorization on every call; the component never reads host `ctx.auth`.
- Public DTOs and validators are closed and versioned. Browser bindings strip local `sessionGeneration` before component operations.
- Participation mutations enforce author ownership and lifecycle constraints against component truth; read capabilities must mirror those rules without replacing mutation authorization.

### Integration Points
- `src/client/internal.ts` and `src/client/server.ts` define the trusted scoped server-client resolver contract.
- `src/component/public/posts.ts`, `src/component/public/feeds.ts`, and `src/component/model/views.ts` produce the post-bearing read DTOs.
- `src/client/contracts.ts`, component validators/generated references, React bindings/hooks, packed fixtures, and static contract tests must move together.
- Phase 3 Plan `03-02` consumes these fields to render exact vote labels and author actions solely from headless truth.

</code_context>
